# MoneyFlow master validation plan

Baseline: `conflict_280926_1750`, commit `382edb64cc965c6db5ee419f3ff8fb5bbdea63ac`. Planning date: 2026-10-19 (America/Chicago). Plan version: 1, frozen initial inventory.

This is a finite validation program, not permission to execute it. Only source/test/document inspection and the five planning documents are authorized now. No Stage 1 test has been executed under this program. Historical results are context, not current acceptance evidence.

## Scope and boundaries

Exactly eight stages, 64 cases, eight cases per stage. The case IDs and finite input variants in TEST_MATRIX.md are the execution contract. One case may contain its explicitly listed variants; this does not authorize arbitrary fuzzing or an expanding investigation. Each variant must receive a recorded result before the case can pass. No extra stages, nested phases, research tasks, production repairs or test-tool development are authorized.

Scope includes the actual account/transaction/debt/payment flows; bills, recurring payments, budgets, goals, categories, summaries, reports, calendars and pagination; local Notes; navigation, dialogs, preferences, localization; and Expo Go/standalone Android reliability. The AI tab is currently a UI-only voice-entry placeholder: test its present navigation/rendering, not speech recognition or AI financial writes. Existing legacy recurring templates are covered only where referenced by current deletion/reference rules. Experimental history APPLY/REVERT, provisioning, migrations, financial repair and public multiuser feature development are excluded. Their presence does not authorize running them.

## Financial test isolation: approval required before execution

1. Offline first: use explicit existing unittest modules whose harness extracts production functions or injects fake clients, synthetic React/Node fixtures and no-network imports. Read setup/teardown before allowlisting. Never use broad unittest discovery or `pytest backend/tests` as a shortcut.
2. For real MongoDB cases, approve a run ID, exact loopback replica endpoint and a new, absent UUID-based database namespace. Existing suites use prefixes such as `moneyflow_r1_temp_<uuid>` and fixed port 27018; review each suite's own prefix, command audit, setup and cleanup rather than assuming a common guard. The existing replica can host a logically isolated test database only after explicit approval of that run and proof that every financial command targets that new namespace. A dedicated test replica is preferable if available, but this plan authorizes creating neither database nor infrastructure now.
3. Protect `development_local_finanzas` and every other pre-existing database. A `test_` prefix alone is insufficient: prove prior absence, exact client/database binding and fixture provenance; record server/replica identity and created database/collection identities. Do not clone real records. Abort on an unapproved namespace or target. Allow only the read-only administrative health commands individually reviewed in the suite. Do not grant permission for arbitrary admin/DDL commands.
4. Fixtures contain only synthetic accounts, users, amounts, categories, notes and history. Use independent Decimal/minor-unit arithmetic and documented sign rules as the oracle, not the response being tested. Start each case from its declared baseline in the approved disposable namespace. Do not use application `/seed`, development reset scripts or global database cleanup. Preserve failed-run evidence; cleanup is allowed only if the exact new namespace and cleanup operation were separately approved. Otherwise retain it and report it.
5. Full HTTP tests require a separately approved test backend process, loopback port 18001 if free, `APP_ENV=test`, explicit `DB_NAME=test_moneyflow_validation_<uuid>`, matching loopback URI and `MONEYFLOW_LOCAL_MODE=0`. `backend/config.py` supports test-mode restrictions. Process values must be verified before importing `backend.server`; review dotenv fallback so every relevant destination/feature variable is explicitly pinned or disabled. Startup may create indexes only in the new test database. Do not use `scripts/dev-backend.sh`: it intentionally forces the personal development database. If the existing harness cannot target the approved namespace without code changes, mark the affected integration case BLOCKED and request a separately scoped change; do not patch it during validation.
6. Existing `backend/tests/test_moneyflow_api.py` is quarantined: its default is a remote preview URL and it includes PUT/POST/DELETE and `/seed`. Do not run it against the current backend or its default URL. Reuse safe existing function-level harnesses instead. The inherited pytest xdist configuration is not itself evidence of isolation; do not change it or permit concurrent suites to share fixtures implicitly.
7. Android financial UI checks use an approved test backend and a separate test application/storage profile populated only with synthetic fixtures. Never repoint the user's running Expo session or clear their Notes/payment journal/storage. Inspect a separate Metro/build process configuration if needed, without modifying `.env`, existing ports or servers. A release APK pointing at the personal backend is unsuitable for destructive UAT.
8. Fault injection, retries and concurrent writes occur only in the approved fake client or test-only process/namespace. Do not disconnect, restart, lock, reconfigure or throttle the user's MongoDB/FastAPI/Metro services. Verify namespace audit and protected-data invariants after integration runs without logging personal records. A failed guard is a stop, never a skipped assertion.

No financial integration tests, process launches, databases, fixtures, command monitors or tools were created/executed during this planning task. Test setup and execution require later authorization; Stage 1 approval alone does not authorize the financial operations in Stages 2–5.

## Findings, severity and bounded diagnosis

- P0 CRITICAL: demonstrated or strongly evidenced corruption, data loss, unauthorized access, incorrect money movement or destructive integrity failure. Stop affected operations, preserve redacted evidence and notify the user. Investigate only the smallest reproducer needed to establish safe boundaries; no automatic repair.
- P1 HIGH: core feature unusable or significant correctness/reliability failure preventing safe completion. Stop its dependent cases; continue independent safe cases. Diagnose only what is needed to establish the blocker within the stage's remaining timebox.
- P2 MEDIUM: bounded functional, visual, navigation, localization or performance defect. Record and continue independent tests; do not recursively investigate.
- P3 LOW: minor defect, speculative optimization, optional refactor or future enhancement. Backlog only.

Test risk is prospective; issue severity requires evidence. Complexity, a warning, a missing benchmark or a hypothetical race does not establish P0. Record an issue before investigating or proposing a repair. Link test ID, evidence, impact, scope-specific release block and next action. Unknowns are NOT TESTED, not defects or passes. Repairs need separate authorization, a fixed patch scope and reruns only of affected frozen cases. Do not add new stages. A demonstrated uncovered P0 may justify one explicit inventory amendment after recording evidence and user notification; all other new ideas go to the backlog, with the original 64-case denominator preserved and any authorized amendment counted separately.

## Evidence and stage decisions

TEST_MATRIX.md defines each case and its reserved evidence ID. Evidence is created only during authorized execution. Each evidence record must include commit/worktree fingerprint, run ID, timestamp/timezone, environment and namespace identity, redacted inputs, expected vs actual result, commands/suite method names, exit codes, per-variant outcomes and relevant screenshots/traces. Do not store secrets, real personal records, full private journals or environment files. Mock, real DB, HTTP, Expo Go and release-device evidence must be labeled separately. Prior conversation results must be rerun at the frozen baseline to qualify.

Case statuses: NOT TESTED, PASS, FAIL, BLOCKED. Mark PASS only after every mandatory listed variant and verification level passes. A mixed mock/device case stays NOT TESTED or BLOCKED until required device work is complete; record partial results in evidence. Stage outcomes: PASSED; PASSED WITH DOCUMENTED NONBLOCKING ISSUES; BLOCKED; INCOMPLETE. PASSED requires all eight cases PASS. PASSED WITH DOCUMENTED NONBLOCKING ISSUES requires all mandatory variants executed, no untested/blocked cases, and only documented P2/P3 failures accepted for the intended scope by the reviewer. BLOCKED identifies an actual prerequisite/safety stop. INCOMPLETE records remaining work/timebox expiry. None can be inferred from source inspection.

PROGRESS.md is the only progress ledger; ISSUES.md is the issue register; RELEASE_READINESS.md governs the decision. A blocked stage does not block unrelated safe stages. Stage 8 may finish its review with a NOT READY decision; that is not equivalent to the application passing validation.

Some use pytest/requests; `backend/pytest.ini` requires pytest-xdist with two workers. Test filenames are candidates, not an execution allowlist.

Several hardcode the personal replica endpoint while creating distinct UUID databases; inspect the exact suite before approval.
